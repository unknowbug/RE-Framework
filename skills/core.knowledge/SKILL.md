# core.knowledge — 知识库生长（L1, inline）

> Spec: engineering-framework-v1.md §6
> Layer: L1 (Static) — 静态约定，写入/查询知识库时使用
> Execution: inline

## 触发场景

- 分析/勘探/审查任何阶段**之前**：先查 `knowledge/INDEX.md`（错误账本置顶）
- 发现可复用模式/新知识：立即写入（不拖到"回头再记"）
- **出现任何错误/失败**（工具报错、验证失败、还原错误、行为不符、崩溃）：立即记录错误账本——**无论是否已解决**

## 知识库优先级（错误 > 正确）

**错误信息是知识库的最高优先级资产**——正确结论只记录"是什么"，错误链条记录"不是什么 + 为什么"：

1. **错误/失败链条**（现象 → 诊断 → 排除 → 发现）优先级最高：先于正确结论写入、INDEX.md 置顶、详细程度最高。
2. **正确信息**（算法指纹/惯用法/确认结论）第二优先级，格式从简。
3. **已排除的错误不删除**：resolved（已排除）与 active（未解决）并列保留——"被排除的假说"与"待解决的错误"同样有价值（标注 ❌/⚠️）。

## 两层结构

```
knowledge/
├── INDEX.md              # 总入口（错误账本置顶，Agent 遇到问题先查这里）
├── builtin/              # 预置知识（项目自带，一般不改）
└── discovered/           # 项目运行中 AI 自动写入
    ├── errors/                       # ★ 错误账本（独立存放，优先级最高，详实度最高）
    │   ├── error-001-<slug>.md       #   每条错误一个文件（含完整诊断/排除链条）
    │   └── error-002-<slug>.md
    ├── compiler-idioms.md          # 编译器/语言惯用法
    ├── f5-bugs.md                  # 还原工具误译模式及修正
    ├── algorithm-fingerprints.md   # 已确认的算法/协议指纹
    ├── anti-patterns.md            # 混淆/反逆向手法
    └── process-lessons.md          # 流程/执行反模式（judge/scout 缺位等复盘教训）
```

## 触发条件 → 写入位置

| 触发 | 写入 |
|------|------|
| **任何错误/失败**（工具报错、验证失败、还原错误、行为不符、崩溃）——**无论是否已解决** | **`errors/error-<NNN>-<slug>.md`**（独立文件，最高优先级，见错误账本格式） |
| 编译器/语言特有的代码生成模式 | `compiler-idioms.md` |
| 还原工具明确误译且有修正方法 | `f5-bugs.md` |
| 确认了算法/协议及其常量/特征 | `algorithm-fingerprints.md` |
| 项目特有的混淆/防御手法 | `anti-patterns.md` |
| **流程/执行反模式**：跳过 judge/scout、retry cap 超限未记录、主会话越界解读、角色错位（如用勘探角色顶替分析） | **`process-lessons.md`**（复盘/反模式记录，防重走） |
| 跨模块通用结构模式 | 新建 `<topic>.md` 或写入对应文件 |

## 执行者规范（spec §4.5 第四条强制触发点）

| 写入对象 | 执行者 | 说明 |
|---------|--------|------|
| 结论性 docs（主题篇/时间线/结论文档） | **MUST subagent 产出草稿** | core.worker 解读产出 → 主会话只应用 + 一致性验证 |
| discovered 结论条目 | MUST subagent 产出（或至少标注产出者） | 结论性内容走 worker；单条简单发现标注产出者 |
| 过程性记录（.investigations 中间产物） | 主会话可写 | 非结论，不强制 |

- 主会话应用草稿时做**一致性验证**：INDEX.md 同步、格式合规、来源定位完整。
- 反模式：主会话直接写结论性 docs = 自评污染（结论未经独立解读）。

## 写入格式（每条独立，不合并）

```markdown
## 发现 #<N>: <简短标题>

**发现时间:** <ISO日期>
**发现者:** <scout/worker/judge — 哪个阶段>
**来源定位:** <触发此发现的地址/字节码偏移/源码位置>
**置信度:** <draft | candidate | confirmed>
**module:** <core | re-binary | re-code | swe>

### 观察
<描述观察到的现象>

### 证据
- <位置>: <具体表现>

### 如何利用
- 下次遇到 <条件> → <应用方式>
```

## 错误账本条目格式（errors/error-<NNN>-<slug>.md，详实度最高）

**每条错误独立文件**，优先级与状态标注必填。详实度要求高于普通条目——完整记录「猜测 → 验证 → 排除 → 发现」全链条：

```markdown
# 错误 #<NNN>: <错误标题>

**优先级:** P0（阻塞/根因未知） | P1（高/影响工作） | P2（中） | P3（低/已排除参考）
**状态:** active（未解决） | resolved（已排除） | false-alarm（误报）
**发现时间:** <ISO日期>
**发现者:** <scout/worker/judge — 哪个阶段>
**module:** <core | re-binary | re-code | swe>
**来源定位:** <触发此错误的地址/字节码偏移/源码位置>

## 错误现象（详细信息）
- 症状: <观察到的错误行为，尽量具体：报错原文/反汇编/回显>
- 影响: <影响范围/阻塞了什么>
- 触发条件: <什么输入/操作触发>

## 诊断过程（完整链条——猜测→验证→排除→发现）
### 假设/猜测
- 假设1: <内容> — <为什么这么猜>
- 假设2: <内容> — <为什么这么猜>
### 验证
- 假设1 → <验证方法> → 结果: <排除 | 部分支持 | 证实>
### 排除
- 假设1 排除原因: <决定性证据>
### 结论（发现）
- 根因: <最终确定的原因>
- 为什么之前会错: <认知偏差/工具误导/信息缺失>

## 排除后的正确认识
- <从该错误学到的正确模式/机制>

## 诊断方法论沉淀
- 下次遇到类似症状 → <第一步做什么>
- 快捷路径: <最高效的诊断线索>
```

## 约束

- 写入后**同步更新 INDEX.md**——**错误账本条目置顶**（索引最前），正确信息条目在错误条目之后。
- **错误优先于正确**：同一分析中出现的错误链条先写；正确结论可后补，错误链条不许拖。
- **已排除的错误同样保留**（resolved/false-alarm 不删），假说排除链条是知识库的核心资产。
- 知识条目带 `module:` 字段：跨模块知识标 `core`。
- builtin/ 与 discovered/ 都没有 → 不做猜测，标注"需要查外部资料"，让用户决定。
- 与 Anchorlaw 关系：知识库内容本身不走 anchor 协议，但**知识结论的验证**走——标 draft 的条目是待验证假设。
